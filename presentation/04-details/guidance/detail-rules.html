Customizing Bob — Guidance

Rules

Rules influence how Bob responds and align its output with your specific preferences and project requirements. They are applied automatically in every session — no prompting required.

Rule example & directory structure

.bob/rules/coding-standards.md Markdown 
# Project Standards & Guidelines

## Code Quality
- Use TypeScript strict mode with explicit return types.
- Prefer pure functions and immutable data structures.
- Run pnpm test and pnpm lint before finishing changes.

## Communication & Style
- Keep explanations direct, technical, and concise.
- Do not add unnecessary comments to self-evident code.
- Reference modified files with exact line numbers.

More info

What rules cover

  • Coding style and naming conventions — enforce your team's preferred patterns consistently across all output.
  • Documentation formats and standards — specify which comment style, README structure, or API documentation format to follow.
  • Testing methods — define which test framework to use, how to name test files, and what coverage expectations apply.
  • Project workflows and team conventions — describe branching strategies, commit message formats, or review checklists.
  • Company policies and guardrails — keep output inside security, compliance, or data-handling boundaries.

Rule scopes & file precedence

  • General rules: Place files in .bob/rules/ to apply across all modes in the project.
  • Mode-scoped rules: Place files in .bob/rules-<mode-slug>/ to load only when that specific mode is active.
  • Global rules: Place files in ~/.bob/rules/ to apply across all workspaces on your machine.
  • File vs Directory: Directory structure (.bob/rules/) is preferred and takes precedence over single files (.bobrules). Files load alphabetically.

Tips & best practices

  • Keep each rule file focused and concise — Bob loads all rules in active scope into the context window at session start.
  • Commit workspace rules to version control so every team member gets identical, standardized behavior.
  • Use mode-scoped rules to avoid loading constraints that only matter in specific workflows.
