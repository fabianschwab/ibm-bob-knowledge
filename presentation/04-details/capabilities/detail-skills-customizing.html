Customizing Bob — Capabilities

Skills

Skills are reusable instruction sets that teach Bob new workflows and specialized tasks. Bob activates them automatically when the task matches — the base prompt stays lean while deep expertise is available on demand.

Skill example & directory structure

.bob/skills/code-review/SKILL.md Markdown 
---
name: code-review
description: Review code for bugs, security
  issues, and best practices
---

## Review checklist
- Check for security vulnerabilities
  and XSS risks.
- Flag missing error handling at
  API boundaries.
- Use severity guide in
  severity-levels.md.
Skills Directory Structure Files 
my-project/
├── .bob/
│   └── skills/                  # Project-scoped skills
│       └── code-review/
│           ├── SKILL.md         # Required — name + description
│           ├── severity-levels.md  # Linked reference file
│           └── scripts/         # Optional utilities

# Global scope (across all workspaces):
~/.bob/
└── skills/
    └── my-global-skill/         # Applied to every project
More info

Why use skills

  • Reusability — define a workflow once and use it across multiple conversations without repeating yourself.
  • Consistency — Bob follows the same approach every time for specific tasks, reducing variation in output.
  • Specialization — create domain-specific expertise for code reviews, testing, documentation, and more.
  • Team collaboration — commit project skills to version control so the whole team benefits from the same standardized workflows.

Three-level loading

  • Level 1 — YAML frontmatter: Always loaded. Just enough for Bob to decide whether to activate the skill. Keep name and description under 1 024 characters.
  • Level 2 — SKILL.md body: Loaded when the skill matches the task. Full instructions and guidelines. Keep it under 5 000 words.
  • Level 3 — Linked files: Loaded only when the specific task explicitly needs them. Place all non-essential reference material, templates, and scripts here.

Tips & best practices

  • Write clear, specific descriptions — Bob relies on them to decide when to activate a skill. Avoid vague names like "code review skill".
  • Keep SKILL.md focused on the core workflow; move detailed checklists and examples to supporting files.
  • Create focused skills with a single responsibility rather than trying to cover multiple unrelated workflows in one file.
  • Project-level skills (.bob/skills/) take precedence over global skills (~/.bob/skills/) with the same name.
