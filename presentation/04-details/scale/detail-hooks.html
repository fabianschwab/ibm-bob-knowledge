Hooks

What they are

Hooks are event-driven automation triggers that fire automatically when specific Bob lifecycle events occur. They run a shell command or send an HTTPS POST — no AI involved. Defined in .bob/settings.json under the hooks key.

  • 7 supported events: SessionStart, UserPromptSubmit, PreCompact, PostCompact, PreToolUse, PostToolUse, Stop.
  • Each hook receives the event payload as JSON on stdin (command) or as a POST body (HTTP).
  • Exit code 2 from a command handler blocks PreToolUse or UserPromptSubmit — the only way to stop Bob mid-action without AI intervention.

How to use them

  • Lint after write: Register a PostToolUse hook with matcher ^(write_file|apply_diff)$ to run ESLint or Prettier automatically after every edit.
  • Block dangerous commands: Use a PreToolUse hook with matcher ^execute_command$ and exit 2 to prevent publishing or destructive operations.
  • Inject context at session start: A SessionStart hook can output dynamic project info to stdout — Bob adds it to the model context.
  • Audit via HTTP: Use an HTTP handler to POST every tool call to an external audit endpoint, with authorization headers from environment variables.
  • Scope to workspace (.bob/settings.json) or globally (~/.bob/settings/settings.json). Both are combined — workspace hooks do not replace global ones.

Trigger

  • Hooks fire automatically — there is no manual invocation. They are purely configuration-driven.
  • The event name and optional matcher (a JavaScript regex against the tool name or session source) determine when a hook runs.
  • Hooks only run in trusted workspaces. Untrusted workspaces silently skip all hooks.
  • Configuration changes for later events take effect immediately. SessionStart changes take effect when the next task starts or resumes.
